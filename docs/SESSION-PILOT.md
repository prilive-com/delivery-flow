# Fresh-session feasibility pilot

This is Experiment B. It is an opt-in study, not the normal session policy.
The owner approved the pilot on 2026-11-16. Each adopter keeps their own
permissions. The full flow, review budgets and tool/model rules still apply.
Do not combine B, the instruction-kernel experiment or Headroom in one slice.

## First inspect three completed handoffs

Use three real completed slices. Keep their exact handoff and original records
in the existing private evidence location. Check these eight items separately:

1. Original requirements and approved scope, including acceptance and exclusions.
2. Owner messages, corrections and decisions, with their original source or a
   usable direct reference. A summary is not a new permission.
3. Deferred findings, their disposition and their trigger.
4. Cross-stage obligations, including a correction that still needs a later check.
5. Mode, review history, round counts, findings and their dispositions. Keep failed
   attempts and any allowed unreviewed-fix marker with its original stage.
6. Baseline, final source, freeze identities and access to complete retained evidence.
7. Each gate's real state and proof, including failed, blocked and unavailable work.
8. The exact next action, open questions, current authority and rollback entry point.

Check the referenced files and their facts. Mark each item PRESENT, MISSING or
UNAVAILABLE with its source and reason. A relative link must resolve from its
recorded origin. A reference into deleted scratch must have a tested restore
route to the full original bytes. Check contradictions and stale state against
the original records. Keep the original handoff unchanged. Record corrections
in the existing working report with a dated pointer to the original.

If information is missing, fix the handoff procedure in a separate reviewed
change before proceeding. Recheck the affected records. Missing original owner
authority cannot be manufactured by a new summary; use a real source or the
flow's existing owner-question rule. Independent work may continue under that rule.

The pilot's template addresses gaps found in ordinary handoffs. It gives the
handoff one current state, one next action and a pointer to the current report.
It links gate results to the revision they tested and deferred findings to
backlog entries with their triggers.

## Then try three new slices

After the historical check succeeds, use three comparable new, complete slices.
Record the pilot choice and each scope before it starts. Use a fresh main agent
session only after the previous slice is complete and its handoff is verified.
Do not reset during a stage or leave a review/gate running without its existing
recovery record. A reviewer leg, subagent, replay or three stages of one slice
are not three completed live slices.

Use the client's supported new-session action. A supported clear action is an
option for a feasibility check after verifying the exact handoff. For a usage
comparison, see the native reader in the [integration guide](DFLOW-INTEGRATION.md).
Use a new process if the reader cannot measure the clear route.
Before starting long work, check a short, completed sample from the same
client version and launch method. Use the intended reader and record the
observed session identity and result. If the reader refuses the sample, keep
the error and original log. Find a supported route or report the measurement
as unavailable. There is no automatic reset,
fixed context cap, early compaction rule or new orchestrator. Read the current
instruction files through the client's real loading chain. The new session must
open the retained handoff and needed originals, confirm all eight items, and
state the correct next action before acting. A mismatch is repaired first;
it never becomes a silent default or permission to repeat an outward action.
Before each reviewer launch, use the current shared reviewer state where the
local profile requires it. A handoff can point to that record. A new session
does not clear a pending quota window.

Keep original requirements, source and full evidence available to implementers
and reviewers. A handoff is a navigation aid, not a lossy replacement. Keep the
existing report, cleanup and recovery rules. No change to another project or
session is authorized merely by participating in this pilot.

## Measure the complete comparison

Record the date range, source revision, flow revision, client version, actual
model/effort, tools, task scope and relevant execution settings for both sides.
Name how comparable the tasks really are and any changed condition. Do not
attribute a difference to new sessions when the comparison cannot establish it.
Compare session methods within each client first. Report another client's
trial as separate evidence unless its baseline also uses that client.

Keep main-agent and reviewer usage separate. Include failed attempts, handoff
work, re-reading and any supervising session in the complete cost. Report fresh
input, cache reads, cache writes and output separately; unknown is not zero.
Measure model calls, compactions, active time, total elapsed time, owner wait,
and process overhead. Weighted cost needs its actual price assumptions;
raw token reduction alone is not a cost or subscription-quota saving.
Use the same start and finish points on both sides. Include startup,
verification after merge, reporting, cleanup and the next handoff. If a
window ends at merge, label it as such and state which work it leaves out.
Report the source and coverage for each subtotal. Record any work needed
to collect the measurement separately if it falls outside the window.

Check lost requirements/decisions, escaped defects, rework, complete gates and
review effectiveness against the same known-defect and known-clean corpus.
Preserve complete evidence. Missing native usage or quality evidence is
UNAVAILABLE; it does not turn an engineering obligation into PASS.

## Adoption and rollback

Three historical and three live slices establish feasibility only. Before normal
adoption, include difficult historical boundaries and live validation in both
Claude Code and Codex with no quality regression. Instruction delivery and
actual compliance need separate evidence. Critical requirement loss blocks
adoption. Keep longer-term quality checks after any pilot and obtain the
owner's adoption decision using the comparison report.

Until that decision, the existing session-continuation behavior remains the
default. Roll back the pilot by using that behavior for new work and retaining
its full handoff and evidence. Never discard an active session or undo its
work merely to restore a comparison. Revert this optional guide through the
normal reviewed delivery path if it is no longer useful.

The [integration guide](DFLOW-INTEGRATION.md) and
[flow](../DELIVERY-FLOW.md) still govern completion and recovery. This pilot
neither proves a saving nor enables the kernel or Headroom.

## Feasibility result

A pilot project merged the three planned slices, L1 through L3, into its
milestone branch in November 2026. One used a new process and two used a
supported clear action. The start checks found one stale tracking reference
and no lost requirement. Later slices that continued in the same session
fall outside this three-slice result. The handoff audit found gaps in two of
three historical records, so the project added a template and filed dated
corrections. Some original gate evidence remains unavailable.

Only the new process yielded main-agent usage in this trial. The other two
logs carried different session IDs in two fields and the reader returned
`SESSION_CONFLICT`. The measured window ended at merge. Changes in scope
and reviewer mix limit the comparison. The project also recorded a quota
rule error during the first live slice. The pilot shows the handoff route
can work. It leaves efficiency and broader adoption open.
