# Instruction-kernel experiment

This is Experiment C. It is a study procedure, not a replacement instruction
file. Keep the full installed instruction chain as the default. The owner
approved the experiment on 2026-11-16; that is not proof of quality or adoption.
Do not combine this trial with B or Headroom in the same slice.

## Start only after B is evaluated

Read the actual B report and its complete handoff evidence. Name whether its
historical checks and three live slices are complete. Missing live evidence is
not a successful pilot. Keep C's runtime trial waiting while that prerequisite
is unresolved. Independent approved work can continue under the current flow.

The baseline inventory, a shorter file or a successful canary is not enough to
replace the normal instructions. Do not change a global loader, import, user
profile or another running session as a side effect of preparing this study.

## Prepare the candidate and the rule map

Use TOKEN-BUDGET section 15 as the starting hypothesis, subject to the newer
owner-approved experiment. Prepare FLOW-KERNEL.md as an isolated candidate
only after the prerequisite. There is no mandatory 200-line cap. There is no
new loader or mandatory hash protocol. Existing step 1 revision provenance
still applies. Full canonical files and engineering evidence remain available.

Inventory each mandatory rule from the current governing documents. Record
its canonical source, who needs it, and the stage and moment that need it.
Keep universally applicable rules always loaded, including owner authority,
accepted requirements, mode and stage order, state meanings, real blockers,
review independence/full access, tests/gates, evidence, resources, delivery,
recovery and cleanup. A shorter summary must not change their meaning.

An isolated candidate may test on-demand loading. A stage procedure leaves
normal always-on loading only after both Claude Code and Codex prove they load
that procedure on demand at the needed stage. Delivery of the copy already
always loaded, read access or a configured filename is not that proof. If
on-demand delivery is unproved, keep the rule always on. Keep machine and
project instructions when testing the candidate.

## Check delivery and compliance separately

For each rule, keep two separate evidence records:

- Delivery: actual native call/instruction evidence shows the needed rule
  reached the right role, session and stage before the relevant action.
- Compliance: the real engineering action and full retained evidence show
  that the rule was followed, including correct refusal and recovery cases.

A quoted canary establishes only what that probe observed. A delivered rule
does not prove compliance; correct behavior once does not prove delivery to
all other sessions. Record unavailable evidence and its effect on the trial.

Compare full instructions and candidate using the same known-defect and
known-clean corpus, same source/configuration, required reviewers, models,
effort, rounds, tests and gates. Cover missing/stale/out-of-order stage text,
owner corrections, deferred findings and cross-stage obligations. Validate
both Claude Code and Codex and their actual instruction-loading chains.
No critical missed defect, skipped obligation or lost evidence is accepted.

Measure complete main/reviewer usage, rereads, cache categories, model calls,
time and operational overhead. Do not claim a saving from file size alone.
No hard context cap, lossy handoff or weaker reviewer routing is introduced.

## Adoption and rollback

Publish actual results and remaining gaps before an adoption decision. No
missing corpus, native-delivery proof or client route can be reported PASS.
The owner's adoption decision follows the evidence; permission to experiment
alone does not install a new default. Keep longer-term quality checks.

Rollback restores the previous instruction-loading arrangement for new work.
Keep active source, full handoffs and retained evidence. Preserve unrelated
operator settings. This study procedure has no runtime loader to remove.
